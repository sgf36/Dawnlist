# WHAT CI INSTALLS IS requirements.lock.txt, NOT THIS FILE.
#
# This one states the floors a person chose and why. The lock beside it pins
# every package and every transitive dependency with hashes, so a build
# installs the same bytes on every runner and a compromised release cannot
# reach a signing job. Regenerate it after ANY edit here:
#
#   uv pip compile requirements.txt --universal --python-version 3.12 \
#       --generate-hashes --no-annotate -o requirements.lock.txt
#
# --universal because the three platforms need one file: a lock resolved on
# Windows omits PyObjC entirely, and `pip install --require-hashes` would then
# build a Mac App Store package whose purchase path cannot import StoreKit —
# which is the failure the PyObjC entries below were added to end. 3.12 is the
# interpreter the build jobs use; the resolution is identical on 3.14, which
# the test job uses.
#
# tests/test_release_workflow.py fails if a floor here is not satisfied by the
# lock, so a raised floor cannot be forgotten.

PySide6>=6.7.0

# 0.77.0 IS THE FIRST RELEASE THAT ACCEPTS `output_config`, and every request

# app/onboarding/interview.py ask for structured output by json_schema, and
# app/main.py passes those dicts straight into messages.create/stream as
# keyword arguments. An older SDK rejects the call with a TypeError naming a
# keyword, which reads like a bug in the caller.
#

# `output_config` parameter and no OutputConfigParam at all; 0.77.0 has both,
# on create and on stream. The floor said >=0.40.0, which would install an SDK
# that cannot make a single working call.

# StoreKit, and THE ONLY WAY A MAC APP STORE BUILD CAN TAKE A PAYMENT.
#
# `app/core/mac_storekit.py` imports StoreKit and Foundation through PyObjC,
# and degrades to `available() == False` when the import fails — deliberately,
# so a Windows or source run is a harmless no-op. Nothing declared PyObjC, so
# the import ALWAYS failed, including in the Mac App Store package: every MAS
# build ever made shipped with the Subscribe button permanently disabled and
# "not available right now" underneath it.
#
# `build_exe.spec` had already listed StoreKit, Foundation, CoreFoundation and
# objc as hidden imports. The 2026-09-09 build log shows what that produced
# without the dependency:
#
#     ERROR: Hidden import 'CoreFoundation' not found
#     ERROR: Hidden import 'objc' not found
#
# — two lines in a log nobody reads, on a build that then succeeded, signed,
# uploaded and reached TestFlight. `packaging/build_macos.py` now REFUSES a
# mas build whose bundle cannot import StoreKit, because a warning here is
# indistinguishable from success.
#
# Markers, not a separate file: a Windows install must not pull these, and a
# second requirements file is a second thing to forget.
pyobjc-core>=10.0 ; sys_platform == "darwin"
pyobjc-framework-Cocoa>=10.0 ; sys_platform == "darwin"
pyobjc-framework-StoreKit>=10.0 ; sys_platform == "darwin"

# START AT SIGN-IN. The daily run happens only while Dawnlist is running, so
# each build needs its own way to be running after a restart.
#
# macOS (both builds): SMAppService.mainApp, from ServiceManagement.
# Microsoft Store: the manifest's startup task, which only
# Windows.ApplicationModel.StartupTask can switch on — a packaged app cannot
# write the Run key for itself. Activation is read to tell a launch at sign-in
# from one by hand, so the first opens in the tray.
#
# All imported lazily in app/core/sign_in.py. Without them the Store build
# opens Windows' own Startup apps page instead, and a Mac build reports the
# switch as unavailable, so a missing package costs the convenience, not a
# crash. The direct Windows build needs none of these: it uses the Run key.
pyobjc-framework-ServiceManagement>=10.0 ; sys_platform == "darwin"
winrt-runtime>=2.0 ; sys_platform == "win32"
winrt-Windows.Foundation>=2.0 ; sys_platform == "win32"
winrt-Windows.ApplicationModel>=2.0 ; sys_platform == "win32"
winrt-Windows.ApplicationModel.Activation>=2.0 ; sys_platform == "win32"
